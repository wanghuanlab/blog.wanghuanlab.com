大模型智能体正在经历从“玩具原型”向“企业生产系统”的深刻蜕变。过去，多智能体常被简单理解为“几个具备不同 Prompt 的 Agent 互相聊天”；而在实际企业落地中，多智能体协作的核心命题已经演化为：**如何构建一套可规划、可调度、可执行、可恢复、可审计的智能体编排与执行体系（Multi-Agent Orchestration Platform）**。

本文基于主流开源框架演进、工程化协议与生产落地实践，对多智能体协作的技术范式、架构设计与落地路径进行全面剖析。

---

## 一、核心趋势：从“对话系统”到“可控执行体系”

在当前的技术演进中，决定多智能体系统可用性的关键**不是 Agent 的数量，而是组织与约束多个独立能力的控制机制**。

目前在生产落地中已形成六大明确的技术共识：

1. **Supervisor / Orchestrator（集中编排模式）**：由主智能体负责需求理解、任务分解、依赖调度、过程质检与成果聚合。
2. **Graph / Workflow（状态图模式）**：通过状态图（State Graph）显式管理任务依赖、分支流转、并行执行与失败重试。
3. **Agent as Tool（智能体工具化）**：将专业子智能体封装为标准的高阶工具（Tool），降低系统调用与上下文耦合度。
4. **协议标准化（MCP + A2A）**：**MCP** 解决 Agent 与外部工具、数据上下文的连接标准；**A2A** 解决跨进程、跨组织 Agent 之间的能力发现与协同通信。
5. **Durable Execution（持久化可靠执行）**：依托持久化任务引擎，确保数小时甚至数天的长任务具备透明暂停、崩溃恢复、超时管理和人工介入（Human-in-the-Loop）能力。
6. **Agent Runtime / Harness 规范化**：将短期/长期记忆、动态沙箱、权限拦截、工具鉴权和链路观测统一整合为标准的运行底座。

### 2.2 核心推荐研究组合

对于企业技术团队（尤其是以 Java 为骨干后端的团队），建议采用 **LangGraph + Google ADK Java + Temporal + MCP/A2A** 作为第一阶段技术研究组合：

* **LangGraph**：掌握多智能体状态机（StateGraph）、中断恢复（Interrupt）与检查点机制；
* **Google ADK (Java)**：验证 Java 原生环境下智能体的注册、组织与 A2A 协议交互；
* **Temporal**：提供生产级长任务保活、状态持久化与故障重试底座；
* **MCP / A2A**：统一工具调用边界与跨服务通信规范。

## 三、多智能体协作的六种核心架构模式

在工程实践中，多智能体协作绝不仅仅是 Supervisor 一种结构，常见的六种模式各有侧重：

```text
┌─────────────────────────────────────────────────────────────┐
│                     多智能体协作拓扑模型                     │
├──────────────────────────────┬──────────────────────────────┤
│ 1. Supervisor (主从协调)     │ 2. Sequential & Parallel     │
│       [Supervisor]           │    [Step 1] ──> [Fork]       │
│      ┌─────┴─────┐           │                  ├─> Agent A │
│  [Agent A]   [Agent B]       │                  └─> Agent B │
│                              │                 [Join] ──> ..│
├──────────────────────────────┼──────────────────────────────┤
│ 3. Handoff (交接棒/接力)      │ 4. Debate / Review (双检对抗)│
│  [Agent A] ──> [Agent B]     │    [Worker Agent]            │
│  (上下文转移 / 控制权移交)    │          │ (提交成果)       │
│                              │          ▼                   │
│                              │    [Review Agent]            │
│                              │    (校验/打回重试)           │
├──────────────────────────────┼──────────────────────────────┤
│ 5. Planner-Executor          │ 6. Agent as Tool             │
│    [Planner] ──> 计划清单    │    [Main Agent]              │
│       │                      │          │ (工具化调用)      │
│       ▼                      │          ▼                   │
│    [Executor] ──> 工具调用   │    [Sub-Agent as Tool]       │
└──────────────────────────────┴──────────────────────────────┘
```

1. **Supervisor（主从协调）**：主控负责全局上下文分派与质检，适合复杂任务，但需设置最大步数防死循环。
2. **Sequential（顺序流）**：标准化步骤线性流转，前序 Agent 的输出直接作为后序 Agent 的输入。
3. **Parallel（并行协作）**：无依赖子任务并行分发（如多维度交叉分析），经 Join 节点统一合并。
4. **Handoff（接力交接）**：Agent 根据当前对话意图直接将控制权转让给另一个 Agent，类似客服中心专家转接。
5. **Planner–Executor（规划与执行分离）**：规划器只出计划清单，执行器逐项调工具，由验证器反馈结果动态修剪计划。
6. **Debate / Review（对抗与审核）**：执行者生成方案，审核者依据规则/风控准则检查，不合格则打回局部重试，形成严密的纠错闭环。

> **架构建议**：生产中往往采用**复合模式**。例如 Supervisor 将子任务并行派发给多个 Worker，经由 Reviewer 进行一致性合规审核，再交给 Executor 触发真实业务。

## 四、关键技术边界：MCP、A2A 与 Temporal 的职责划分

在技术选型中，这四种组件常被混为一谈。事实上，它们处于不同的技术层级与边界：

```text
+------------------------------------------------------------------------+
| 业务流程持久化层：Temporal                                            |
| (负责跨机器重启恢复、几周级长任务保活、Saga补偿、重试、确定性状态机)   |
+------------------------------------------------------------------------+
       │ 驱动运行
       ▼
+------------------------------------------------------------------------+
| 智能编排与决策层：Google ADK / LangGraph                                |
| (负责意图识别、动态规划、Prompt装配、状态分支选择、结果质检)          |
+------------------------------------------------------------------------+
       │                                                │
       ▼ (能力横向互操作)                              ▼ (工具垂直下钻)
+-------------------------------+              +-------------------------+
| 跨 Agent 协议：A2A            |              | 工具标准化协议：MCP      |
| (多独立部署智能体之间的契约通信)|              | (标准化读取DB、API、设备)|
+-------------------------------+              +-------------------------+
```

| 技术组件 | 解决什么问题 | 本质定位 | 典型举例 |
| :--- | :--- | :--- | :--- |
| **MCP** | Agent 如何安全发现、调用外部工具及获取上下文 | **工具与上下文接入协议** | 调用高精地图、查询天气、执行 SQL、读取 MinIO 文档 |
| **A2A** | 独立部署的 Agent 之间如何发现能力、分发任务与同步结果 | **跨智能体互操作协议** | 调度中心 Agent 调用独立的“航线规划 Agent”并获取航线包 |
| **LangGraph / ADK** | 如何组织智能体内部的决策逻辑、状态转移与人机介入 | **Agent 编排与运行框架** | 条件路由、状态图迁移、Interrupt 人工审批挂起 |
| **Temporal** | 任务如何长期可靠运行、故障自动恢复、防丢状态 | **持久化工作流执行平台** | 巡检任务执行 6 小时中途服务节点重启，状态无缝恢复 |

> **关键提醒**：Temporal 保证的是**控制流调度的持久化与确定性**，外部真实操作（如设备控制、资金扣款、工单创建）必须在业务层保证**接口幂等**与**补偿机制（Saga）**。

针对以 Java 为骨干的企业应用，应将多智能体协作平台解耦为三大平面：**协作控制平面**、**智能体执行平面**与**能力数据平面**。

### 5.1 生产落地的三大黄金法则

1. **以任务（Task）为核心，Agent 仅是执行资源**：
   * 用户发起的是业务任务，不是与某个 Agent 的聊天。任务具备持久的 `taskId`、明确的生命周期、操作审计与成果包。Agent 可以被升级或替换，但任务状态永不丢失。
2. **智能决策与确定性业务控制严格物理隔离**：
   * 大模型仅负责**模糊推理、方案生成、信息提取与初审**；
   * 确定性代码与状态机（Java + Temporal）负责**权限强校验、重试熔断、敏感操作审批、幂等调用与设备控制**。
3. **接口由 Schema 强契约驱动，杜绝纯自然语言口头约束**：
   * 所有 Agent 的输入、输出参数必须具备严格的 JSON Schema 结构定义，失败时必须抛出标准错误码（ErrorCode）与局部补偿上下文。

### 5.2 统一任务状态模型

```text
[CREATED] 
   └──> [CLARIFYING] (需求澄清)
           └──> [PLANNING] (方案规划)
                   └──> [WAITING_APPROVAL] (人工审核断点)
                           └──> [READY] 
                                   └──> [RUNNING] ──> [COMPLETED]
                                           │
                                           ├──> [PAUSED] (异常挂起)
                                           ├──> [FAILED] (失败留痕)
                                           └──> [CANCELLED]
```

对于失败场景，建议在数据库中明确持久化 `failureCode`、`retryCount`、`lastCheckpoint` 与 `compensationStatus`，而不只是一段简单的文本日志。

## 六、场景落地实操对比：企业协同 vs 边缘勤务

通过两个典型 PoC，可以全面覆盖不同维度的技术考量：

| 验证维度 | 场景 A：企业协同（软任务）<br>*例：新项目启动人资/研发/预算立项方案* | 场景 B：设备/无人机勤务（硬任务）<br>*例：高架路段巡检与交通事件闭环* |
| :--- | :--- | :--- |
| **主任务特征** | 跨领域数据汇总、多专家观点整合、文档产出 | 长时巡航保活、多源数据感知、物理安全强约束 |
| **协作核心** | Supervisor 拆解 $\rightarrow$ HR/财务/研发并行 $\rightarrow$ 审查员打回修正 | Planner 规划航线 $\rightarrow$ 静态合规校验 $\rightarrow$ 硬件执行 $\rightarrow$ CV检测 $\rightarrow$ 动态重规划 |
| **长任务恢复** | 依赖较低（小时级断点重启即可） | **至关重要**（服务重启后必须立即恢复对在途无人机的状态监视） |
| **动态重规划** | 较低（多是一次性成文） | **极高**（突发恶劣天气、电量不足或突发事故时需动态修剪计划） |
| **工具安全要求** | 中（数据脱敏与权限准入） | **极高**（**LLM 绝不能直接向真实硬件发裸指令**，必须过确定性安全屏障） |
| **建议首选框架** | Google ADK Java 或 LangGraph + PostgreSQL | Temporal 流程持久化 + 规则校验引擎 + ADK/LangGraph |

## 七、面向团队的工程实践：渐进式技术栈与度量体系

### 7.1 推荐技术栈选型

* **后端主框架**：Java 21 + Spring Boot 3.x
* **Agent 编排引擎**：Google ADK Java（优先融合） / LangGraph Python（复杂图编排备选）
* **长任务引擎**：Temporal Java SDK
* **协议层**：A2A（智能体间互联） + MCP（外部工具接入）
* **持久化与消息**：PostgreSQL + Redis + Kafka
* **可观测性**：OpenTelemetry + Prometheus + Jaeger

### 7.2 建议的 8 周敏捷落地路线图

* **第 1–2 周（基础架构原型）**：完成基于 Google ADK Java 或 LangGraph 的 Supervisor + 3 Agent 原型，跑通任务拆分、调度与结构化返回；
* **第 3–4 周（完整多智能体闭环）**：实现规划器（Planner）、并行执行、多检审核（Reviewer）机制，打通局部重试与上下文修剪；
* **第 5–6 周（工程化加固）**：引入 Temporal 实现长任务保活，打通 MCP 工具网关，增加人工审批断点（Interrupt）与 OpenTelemetry 全链路 Trace；
* **第 7–8 周（多业务移植验证）**：将统一底座分别对接办公室协同与无人机数字孪生环境，验证“新增一个业务 Agent 无需改动核心控制底座”。

### 7.3 工程化度量指标（SLO）

拒绝“主观感觉好不好”，必须建立基准测试集并量化以下指标：

| 评估维度 | 首轮 PoC 目标指标 | 衡量方式 |
| :--- | :--- | :--- |
| **任务成功率** | 基准任务集 $\ge 90\%$ | 自动化测试集定期回归 |
| **任务拆解有效率** | $\ge 95\%$ | 评估计划步骤是否合理、无冗余 |
| **工具参数正确率** | $\ge 99\%$ | 参数校验拦截与报错统计 |
| **非授权操作拦截** | $100\%$ | 权限网关攻击与越权模拟测试 |
| **崩溃恢复测试** | 100% 恢复成功 | 人为 kill 服务节点后的任务自愈测试 |
| **链路追踪完整度** | $100\%$ | 每次模型调用及工具调用均具备关联 Trace ID |

## 八、总结与源码精读建议

构建多智能体系统，绝非给大模型多套几个角色名称的 Prompt 那么简单：

1. **架构定位**：不要将项目做成一个玩具级的“Agent 聊天室”，要坚决将其建设为 **企业级多智能体协同编排平台（MAOP）**。
2. **能力复用**：将**任务调度、动态规划、能力发现、契约通信、异常补偿、人工介入与全链路可观测性**沉淀为共享基座。
3. **技术归宿**：上层模型会不断变聪明、上下文窗口会越来越大，但**确定性的业务控制、权限隔离、数据合规与长任务高可用**，永远是系统架构师不可替代的工程壁垒。

### 必读源码推荐
